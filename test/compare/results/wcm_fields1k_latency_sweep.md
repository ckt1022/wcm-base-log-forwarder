23,250 EPS 的整段吞吐判定仍 PASS，但最後 30 秒的 p99 已升至
214.5 ms；23,500 EPS 的 p99 又随時間持續增長。因此：

- **延遲 knee 位於 23,000–23,250 EPS**。
- **23,000 EPS 是本輪三分鐘內的最高延遲穩定點**，但 CPU 平均已達
  96.89%，不適合作為生產安全點。
- **23,500 EPS 雖然仍通過原吞吐規則，但不是延遲穩態**；這說明只看
  drain 後實收量會高估可服務容量。
- 過載區各點的整段分位數不必單調；每輪的 batch/channel 相位與背壓時點
  會改變數值。所有超過 23,500 EPS 的實驗都已顯示非穩態排隊。

## 40 MiB / 25K OOM 對照

- 容器成功啟動，但 WCM mem-guard 在自報 29 MiB（高於 40 MiB 的 70%
  高水位）就執行 `PAUSE input`。
- 恢復低水位為 22 MiB，但程序基線無法降到該值；180 秒負載期間 sink
  始終收到 0 筆，最後由 runner 270 秒保險超時結束。
- Docker 最終記錄 `OOMKilled=false`；故障模式是 **fail-closed 永久停流**，
  不是 OOM kill。
- 恢復 512 MiB 後的 2,500 EPS 短測立即 PASS，證明主機、image 與 pipeline
  沒有被破壞。

Docker memory cgroup 會將真正 OOM 的影響限制在容器內；主機通常不會因此壞掉，
但容器會被終止，未落盤 buffer 可能遺失。本次因 mem-guard 先介入，並未走到
核心 OOM kill。

## 操作建議

- **20,000 EPS**：p99 129.764 ms、p99.9 148.098 ms，CPU 平均/最高
  83.87%/90.80%，是較合理的高負載操作點。
- **22,500 EPS**：延遲仍穩定，但 CPU 平均 94.81%，只適合壓測，不建議
  作為長期生產點。
- memory limit 不能低於程序基線再搭配 70%/55% guard。若必須用小記憶體，
  需同時重新設定 guard 水位、WASM prewarm/heap 與 channel/buffer，不能只把
  Docker limit 改為 40 MiB。
