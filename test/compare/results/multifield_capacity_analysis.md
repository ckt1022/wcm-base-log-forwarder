# 多欄位 JSON 容量曲線分析（128–2048 B）

## 測試範圍

共同外部條件為 1 CPU、512 MiB、TCP 單連線、1 秒 flush、單 output
worker/concurrency、retry 關閉、60 秒負載加 20 秒 drain，五條訊息循環中保留
warn/error（40%）。容量點均以 generator 達成率、send lag、backlog、實收筆數與
OOM 共同判定。

本圖的 workload 同時增加大小與 top-level 欄位數：

| JSON bytes | 欄位數 |
|---:|---:|
| 128 | 4 |
| 256 | 8–9 |
| 512 | 17–18 |
| 768 | 27 |
| 1024 | 36 |
| 1536 | 54 |
| 2048 | 72 |

因此曲線表示「大小與欄位同比增加」的綜合成本，不能只由這張圖把 per-byte 與
per-field 成本完全分離。

128 B 點依指定使用 `ts`/`level`/`msg`/`att` 四個 top-level 欄位，保留
`att.service` 與 `att.code`，並移除 `_slot`。為容納完整 timestamp 而縮短了
message/service 值；因此它適合觀察小 record 的固定成本，但與 256 B 的差值
不應解讀為只有 bytes 造成。

## 正式容量

| 大小 | FB Lua MB/s | Fluentd MB/s | WCM MB/s | Vector MB/s | FB WASM MB/s |
|---:|---:|---:|---:|---:|---:|
| 128 | 41.021 | 26.315 | 20.898 | 10.707 | 4.128 |
| 256 | 53.969 | 35.491 | 23.129 | 14.392 | 4.883 |
| 512 | 64.124 | 34.627 | 23.700 | 15.390 | 5.386 |
| 768 | 66.133 | 48.446 | 24.992 | 15.380 | 5.306 |
| 1024 | 69.186 | 53.299 | 25.624 | 15.375 | 5.535 |
| 1536 | 66.397 | 52.718 | 24.591 | 14.601 | 5.226 |
| 2048 | 65.566 | 54.297 | 24.587 | 13.523 | 5.020 |

EPS 在 MB/s 進入平台後必然近似反比於單筆大小，所以 EPS 曲線持續下降不是額外的
效能退化。判斷引擎是否退化應主要看 MB/s 與正規化曲線。

## 成本模型

可用以下模型解釋整體形狀：

```text
每筆 CPU 成本 ≈ a（逐筆固定成本）
              + b × bytes（parse/copy/encode）
              + c × fields（map traversal/allocation）
              + h（GC、cache、chunk、ABI 等非線性成本）
```

小 record 時，固定成本 `a` 佔比高，增加 record 大小可攤薄固定成本，使 MB/s
上升。本 workload 又讓 `fields ≈ k × bytes`，當線性 byte/field 成本開始主導時，
MB/s 會趨近產品自己的平台。若 `h` 隨 map 變大而增加，平台之後會緩慢下降。

## 各產品曲線

### Fluent Bit Lua

- 128→256→512 B 從 41.021→53.969→64.124 MB/s 上升，清楚顯示小 record 的
  Lua callback、table 建立與 engine record 固定成本。
- 512–2048 B 維持 64.124–69.186 MB/s；768 B 的 66.133 MB/s 確認在平原上。
  手動重測的 1024 B 在 67,500 EPS 三輪均 PASS（69.186 MB/s）；
  68,000 EPS 因 generator send lag p99 為 50 ms 而 FAIL。2048 B 比新峰值低
  5.2%，約在各大小容量搜尋解析度的上緣，可能有輕微下降，
  但整體仍以約 64–69 MB/s 平台解讀。
- 平台高度最高，表示 native input/output engine 加 Lua filter 的整體線性成本最低。

### Fluentd

- 128 B 只有 26.315 MB/s，到 256 B 升為 35.491 MB/s，證明 Ruby Hash/plugin
  callback 的逐筆成本在小 record 區間非常明顯。
- 256/512 B 都約 35 MB/s，768 B 已升到 48.446 MB/s，1024–2048 B 為
  53.299–54.297 MB/s。768 B 證明 1024 B 不是孤立異常；主要轉折發生在
  512–768 B，然後逐漸靠近較高的平原。
- 手動重測的 1024 B 在 52,000 EPS 三輪均 PASS（53.299 MB/s）；
  52,500 EPS 四輪中兩輪 PASS、兩輪因 generator send lag 超過
  10 ms 而 FAIL，因此將 52,500 EPS 定義為首個不穩定點。
- 合理假設包括 Ruby 每筆 Hash/plugin callback/GC 成本被較大 record 攤薄，及
  1 MiB memory buffer 在較少 records-per-chunk 下進入更有效率的配置與 flush
  節奏；目前沒有 allocation/GC profile，不能在這些假設中選定唯一原因。
- 若要再定位轉折形狀，640 B 是比 896 B 更有價值的單一補點；但對整體
  結論而言，768 B 已排除 1024 B 孤點異常。

### WCM

- 128 B 為 20.898 MB/s，256–2048 B 在 23.129–25.624 MB/s；小 record 仍有固定
  成本，但下降幅度比 Lua/Fluentd/Vector 小。七點中仍是最接近
  水平平台的產品。
- 代表在 256 B 時，batch-granular WASM pipeline 的 parse、欄位轉換、跨 ABI
  資料搬移與 format 成本已占主導；逐筆固定成本的額外攤薄不明顯。
- 手動重測的 1024 B 三輪均在 25,000 EPS（25.624 MB/s）PASS，
  25,500 EPS 三輪均因 backlog 超過三秒門檻 FAIL。1536/2048 B 約比
  1024 B 低 4%，仍接近容量搜尋解析度，尚不足以主張大 record 明顯退化。

### Vector

- 128→256→512 B 從 10.707→14.392→15.390 MB/s 快速上升，之後才進入約
  15–16 MB/s 平原。
- 512/768/1024 B 分別為 15.390/15.380/15.375 MB/s，形成清楚平原。
  手動重測的 1024 B 在 15,000 EPS 三輪均 PASS（15.375 MB/s）；
  15,500 EPS 因 generator send lag p99 為 500 ms 而 FAIL。之後降到
  14.601、13.523 MB/s；
  2048 B 比峰值低 12.1%，大於容量搜尋誤差，應視為真實下降訊號。
- 可能來源是 VRL 對每個欄位執行 lookup、string conversion 與 `set!`，map 變大後
  allocation、hash table 與 cache locality 成本提高；JSON encode 也必須重新走訪
  完整輸出物件。
- 需要 1280 B/45 欄位點判斷下降是在 1024 B 後立即開始，還是在更接近 1536 B
  才發生。

### Fluent Bit WASM

- 128→256→512 B 從 4.128→4.883→5.386 MB/s 上升，但左側斜率小於 Lua、
  Fluentd 與 Vector，表示 WASM/JSON 線性成本在小 record 時已占很大比例。
- 512/768/1024 B 分別為 5.386/5.306/5.535 MB/s，仍可視為約 5.3–5.5 MB/s
  的平原。手動重測的 1024 B 在 5,400 EPS 三輪均 PASS（5.535 MB/s）；
  5,500 EPS 三輪中兩輪 PASS、一輪因 generator send lag p99 為 500 ms 而
  FAIL，因此定義為首個不穩定點。之後降至 5.226、5.020 MB/s；2048 B
  比峰值低 9.3%，同樣高於搜尋誤差。
- 除 JSON/map 成本外，每筆 record 進出 WASM filter 的序列化、ABI 呼叫與記憶體
  配置會放大多欄位物件成本；結果顯示最佳區域在約 1024 B/36 欄位附近。

## 少欄位對照提供的證據

現有 1024 B 少欄位與 36 欄位容量可直接控制 JSON 大小。多欄位相對少欄位的
MB/s 保留率如下：

| 產品 | 1024 B 少欄位 | 1024 B／36 欄位 | 保留率 |
|---|---:|---:|---:|
| FB Lua | 143.497 | 69.186 | 48.2% |
| Fluentd | 75.848 | 53.299 | 70.3% |
| WCM | 75.848 | 25.624 | 33.8% |
| Vector | 61.499 | 15.375 | 25.0% |
| FB WASM | 19.475 | 5.535 | 28.4% |

相同 1024 B 下只改欄位結構就造成 30–75% 的 throughput 損失，證明多欄位曲線
主要不能用純 byte bandwidth 解釋；欄位數與物件操作是核心變因。

## 建議補測

### 最小曲線補點（優先）

1. **1280 B／45 欄位，至少 Vector 與 FB WASM；最好五產品都做**：定位兩者在
   1024–1536 B 的轉折點。
2. **640 B／約 22–23 欄位，只做 Fluentd**：若需要更精確描述 512–768 B 的
   上升形狀，這是最省成本的單點。

若目標是解釋目前的主要異常，1280 B 對 Vector/WASM 的價值高於再細分
Fluentd；640 B 是可選的精緻化點。

### 若要畫平滑的論文曲線

再加 **1792 B／63 欄位**，形成 128、256、512、768、1024、1280、1536、1792、2048 B
的近似等距序列。但 1792 B 對機制判別的價值低於 768/1280 B。

### 若要證明原因，而不只是補平曲線

增加大小仍同時改變 bytes 與 fields，無法辨識因果。最有價值的是二組正交控制：

1. **固定 1024 B，欄位數 9、18、27、36**：直接量測 per-field 成本與是否非線性。
2. **固定 36 欄位，大小 1024、1536、2048 B**：只延長既有 value，量測純
   per-byte/copy/encode 成本。

若只能再做一輪，建議先跑 1280/45；若目標是寫出可信的機制結論，
則正交控制比再增加更多單純大小點更重要。
